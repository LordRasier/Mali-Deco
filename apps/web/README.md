# Storefront

La portada y `/catalogo` consumen el catálogo y los ajustes publicados de la API. Configurar `API_BASE_URL` con el prefijo completo, por ejemplo `http://127.0.0.1:3001/api/v1/`. El nombre visible viene de `/catalog/settings`. Si falta configuración o falla la API, se muestra un error: **nunca** se sustituyen productos o filtros reales por datos ficticios. En producción se requiere un ingreso del mismo origen para `/api/v1/*`.

Para revisar el concepto sin base de datos, iniciar Next en desarrollo con `STOREFRONT_MODE=demo`. Es una opción explícita de desarrollo; no se admite en producción. Las imágenes, precios y clasificaciones de la demo son sintéticos y están señalados como ejemplos. Los IDs de la demo y las claves `storefront-cart-v1-demo` / `storefront-cart-v1-api` se mantienen separados. No hay checkout, pagos, envíos ni promesa de disponibilidad o reserva; `supplyMode` no es stock.

## Catálogo y carrito

`/catalogo` consulta productos paginados y metadatos de filtros reales. La URL representa la búsqueda, categorías, materiales, colores, moneda, límites de precio en unidades menores, orden y página; volver/adelantar y compartir conservan el estado. Los valores dentro de un grupo son OR y los grupos son AND; material, color y precio deben coincidir en una misma variante. Los metadatos son globales para la moneda, no recuentos dinámicos. El servicio limita cada lista a 200 opciones y la UI avisa si está truncada. Los filtros desconocidos no amplían los resultados. El primer código de moneda devuelto por la API se selecciona solo cuando la URL no especifica uno; nunca se presupone ARS en el catálogo real.

Los campos de precio aceptan coma o punto decimal **sin separador de miles**; la conversión utiliza la precisión de la moneda y enteros, sin redondeo flotante. Al limpiar se conserva la moneda vigente. La vista móvil mantiene cambios sin aplicar hasta confirmar; cancelar los descarta. Carga, cero resultados y error de API son estados distintos.

La grilla usa el resumen y variante coincidente del listado, sin una petición de detalle por tarjeta. Abrir una tarjeta carga su detalle y páginas de variantes a demanda. Si la variante coincidente no está en la primera página, se valida por separado antes de permitir agregarla. El carrito se resuelve contra `/catalog/cart/resolve` en lotes de hasta 100 pares, no contra la página visible. Solo una partición completa y válida de todos los lotes permite retirar pares expresamente ausentes; un fallo o una respuesta incompleta conserva líneas y muestra verificación pendiente. Los importes se separan por moneda y los subtotales usan enteros exactos. Las imágenes del catálogo real siguen siendo marcadores neutros hasta que la API publique imágenes.

Verificación: desde la raíz, `npm run lint`, `npm run typecheck`, `npm test` y `npm run build`. Las pruebas del storefront también se pueden ejecutar con `npm test -w @store/web`. No se debe usar el modo demo para vender ni asumir que este slice habilita transacciones reales.

## Administración de catálogo (slice de desarrollo)

La ruta `/admin` usa la API real: inicio/cierre de sesión, consulta y gestión de productos, variantes y taxonomías (categorías, materiales y colores). Los roles `owner` y `catalog` pueden gestionar el catálogo; `operations` puede iniciar y cerrar sesión, pero no editarlo. Los registros archivados son de solo lectura y no existe restauración. Las políticas de abastecimiento no son cantidades de inventario. Ventas, pedidos, stock, imágenes, pagos, envíos y ajustes administrativos aún no están implementados. No se simula el guardado ni se crean credenciales o cuentas de ejemplo.

Para desarrollo, use **exactamente** `http://127.0.0.1:3000` en el navegador y configure la API con `ADMIN_ORIGIN=http://127.0.0.1:3000`. Next redirige internamente `/api/v1/*` a `http://127.0.0.1:3001/api/v1/*` únicamente en desarrollo; el navegador sigue en el mismo origen. Opcionalmente, `DEV_API_PROXY_ORIGIN` cambia el puerto de destino mediante un origen HTTP canónico de `127.0.0.1`, sin ruta, credenciales, consulta ni fragmento. Esta opción es exclusiva del servidor de desarrollo y no debe confundirse con `API_BASE_URL`, que incluye `/api/v1/` para el storefront.

La sesión se mantiene en la cookie HttpOnly de Nest; el token CSRF permanece solo en memoria. Una recarga verifica la sesión y solicita un token nuevo. Distintas pestañas pueden invalidar mutuamente ese token: si se recibe un error de CSRF, recargue y revise antes de volver a enviar, sin asumir que una operación se completó. El servidor sigue siendo la autoridad para permisos y validaciones.

En producción el rewrite de Next está desactivado. Se requiere un ingreso HTTPS del mismo origen que envíe `/api/v1/*` a Nest y el resto a Next, preserve `Origin`, cookies y `X-CSRF-Token`/`Set-Cookie`, no almacene en caché respuestas de autenticación o administración y mantenga Nest privado. **Bloqueante de producción:** el limitador de inicio de sesión actual cuenta 10 intentos por 15 minutos por IP de conexión y cuenta, incluidos los exitosos. Tras un proxy, los clientes comparten el presupuesto de IP. Se necesita un diseño de ingreso/IP confiable revisado por separado; un limitador en el borde por sí solo no restablece el aislamiento por cliente. No habilitar `trust proxy` sin esa revisión.

La interfaz aún no se ha validado con MySQL, credenciales reales ni en un navegador real. Aplicar migraciones, crear la cuenta inicial y desplegar requieren sus propios pasos y autorización; no forman parte de este slice.

# Cotización Zipnova: base desconectada

Este corte agrega un adaptador de opciones múltiples, un resolver de catálogo y la ruta `POST /api/v1/shipping/quote`. Por defecto la ruta devuelve `DISABLED` antes de consultar catálogo o red. Existe una activación explícita preparada para después de revisar todos los requisitos; las pruebas usan transporte ficticio. La implementación existente de Andreani no cambia.

El adaptador recibe identificadores, cantidades y destino; un resolver inyectado debe consultar precios, productos y embalaje del servidor. Sin catálogo o datos logísticos devuelve indisponibilidad antes de invocar el transporte. El usuario indicó que agrupa los artículos: `items` con `type_packaging=dynamic` envía una entrada por cada unidad comprada, para que Zipnova agrupe según la configuración de la cuenta. No se usa cada unidad como bulto ni se inventa una caja. También se admite la alternativa de bultos previamente resueltos.

Se usa `account_id` y `origin_id` explícitos. Peso en gramos y medidas en centímetros enteros: para `items` los milímetros se redondean hacia arriba al siguiente centímetro, sin subdeclarar ni añadir otro margen; para bultos ya definidos se exige conversión exacta. No se redondean pesos inferiores al mínimo permitido. El valor declarado usa precisión monetaria configurada y, al enviarse como número JSON, se rechaza si alcanza `10^(15-exponente)` o si el catálogo detecta pérdida de precisión. Se toma `amounts.price_incl_tax` del comprador conservando el texto numérico original de JSON antes de su conversión a unidades menores, sin sumar IVA ni multiplicar por bultos; moneda configurada explícitamente. Se ignoran resultados no seleccionables y puntos de retiro ausentes; para retiro se conserva `point_id`. En modo dinámico se valida y conserva el número de bultos devueltos por Zipnova. La opción seleccionada se suma con enteros exactos al subtotal solo si todo está en la misma moneda; se invalida ante cambios de carrito, precio o destino. El adaptador distingue fallos de configuración, catálogo, logística, destino, autorización, límite, timeout, respuesta y ausencia de opciones.

La cuenta tiene seleccionado empaquetado dinámico con límite de lado 150 cm y peso 30.000 g. Zipnova intenta minimizar bultos, pero puede generar más de uno. La guía no confirma cómo añade protección o tara de la caja; no se agregan valores inventados. Debe acordarse y verificarse qué protección está incluida en las medidas cargadas para cada unidad y contrastar bultos calculados con pedidos físicamente embalados. La API no documenta moneda en la respuesta de cotización. No hay sandbox confirmado. No se probó tarifa real, ni se creó o pagó envío. Antes de activar: validar catálogo y precios con la base de datos elegida, logística, moneda, origen, credenciales y permisos; conectar el flujo y probarlo. No incluir credenciales en archivos versionados, logs o cliente.

## Transporte y futura entrada local

La ruta está desactivada salvo que `NODE_ENV=development` y `ZIPNOVA_ENABLED=true`. En producción permanece desactivada incluso con esas credenciales. Para habilitarla también exige `ZIPNOVA_OPERATOR_ORIGIN` con el origen exacto del navegador local, por ejemplo `http://127.0.0.1:3000`, y `ZIPNOVA_LOGISTICS_VALIDATED=true`, una afirmación explícita del operador que solo debe establecerse después de verificar medidas, peso, protección y embalaje contra la operación real. Requiere `ZIPNOVA_ACCOUNT_ID` y `ZIPNOVA_ORIGIN_ID` enteros positivos, `ZIPNOVA_CURRENCY` en código de tres letras mayúsculas, `ZIPNOVA_CURRENCY_EXPONENT` explícito entre 0 y 3, y `ZIPNOVA_API_TOKEN` y `ZIPNOVA_API_SECRET` válidos como formato. Una configuración incompleta devuelve `CONFIG_UNAVAILABLE`; la ausencia de catálogo o medidas devuelve indisponibilidad antes de la red. La confirmación del operador no verifica por sí misma que los datos o permisos sean correctos.

API y servidor web de desarrollo escuchan en `127.0.0.1`. Tanto el proxy como la API verifican origen y Host exactos, POST JSON y rechazan `Sec-Fetch-Site: cross-site`; la API también comprueba la dirección local del socket. No usar túneles ni exponer puertos. Esta barrera es para pruebas locales y supone confiables los procesos del equipo; no sustituye autenticación, controles distribuidos ni seguridad para producción.

El transporte usa solo el endpoint fijo de cotización, rechaza redirecciones, establece timeout y limita respuestas; no crea envíos. Por proceso admite hasta dos solicitudes simultáneas y diez por minuto; ante un 429 respeta `Retry-After` o espera un minuto si falta o es inválido. La cotización recibe un plazo interno máximo de cinco minutos, tras el cual el carrito descarta la selección y pide volver a cotizar; no es garantía de precio del transportista ni tiempo estimado de entrega. Las pruebas usan exclusivamente `fetch` simulado. No activar hasta validar DB, cuenta, origen, moneda, logística, controles de abuso, vigencia de cotización y una prueba real controlada. La configuración vive en el proceso del servidor, nunca en el navegador ni en logs.

Para una futura configuración local, el usuario puede ejecutar desde la raíz del proyecto `powershell.exe -NoProfile -File .\scripts\setup-zipnova-local.ps1` en su propia consola. El script solicita token y secret con entrada oculta, usa la carpeta local del usuario resuelta por Windows (normalmente `%LOCALAPPDATA%\MaliDeco-Zipnova\zipnova.env`), verifica que no esté dentro de un repositorio Git ni atraviese enlaces, restringe la carpeta nueva al usuario y deja `ZIPNOVA_ENABLED=false`. No sobrescribe una carpeta existente ni acepta argumentos o credenciales en la línea de comandos. El archivo guarda texto sin cifrar y requiere proteger la cuenta y sus respaldos; no debe copiarse al chat, repositorio o almacenamiento sincronizado. El script admite solo caracteres seguros para el formato. La versión anterior se probó con valores ficticios; la protección de ruta actual se prueba sin ingresar credenciales.

Tras compilar, Node 24 puede cargar el archivo privado antes de iniciar la API, por ejemplo desde PowerShell con `$zipnovaEnvFile = Join-Path ([Environment]::GetFolderPath('LocalApplicationData')) 'MaliDeco-Zipnova\zipnova.env'` y luego `node --env-file="$zipnovaEnvFile" apps/api/dist/main.js`. La configuración de DB y los demás valores requeridos deben estar disponibles para el proceso. Las variables ya presentes en el entorno prevalecen sobre el archivo: revisar en particular que no exista un `ZIPNOVA_ENABLED` heredado inesperado, sin imprimir credenciales. Cambios en el archivo o entorno requieren reiniciar el proceso. No se ha ejecutado el helper con credenciales reales ni activado la conexión.

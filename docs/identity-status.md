# Identidad administrativa: pendiente de verificación independiente

La migración agrega tablas para administradores, sesiones y límites de intentos. No crea usuarios ni credenciales predeterminadas. La prueba aislada de migración y operaciones de identidad pasó en MariaDB 10.4.32, con modo estricto exclusivo de la conexión de prueba; la configuración de la aplicación conectada y la revisión de producción siguen pendientes.

Configure `ADMIN_ORIGIN` con el origen exacto de la interfaz (HTTPS obligatorio en producción). La API y el frontend deben servirse bajo el mismo origen mediante un proxy: no se habilita CORS. El proxy debe evitar acceso directo a la API y aplicar su propio límite de solicitudes; el límite de la aplicación usa la IP de la conexión sin confiar en cabeceras reenviadas. Detrás de un proxy, esa IP puede ser compartida por todos los visitantes. Las ventanas de intentos persistidas necesitan limpieza operativa periódica.

Los emails administrativos admiten solo caracteres ASCII imprimibles y se normalizan a minúsculas tras quitar espacios exteriores; bootstrap y login comparten la regla. La búsqueda usa comparación exacta por bytes y la unicidad usa colación binaria; la base exige ASCII en minúsculas sin espacios. La migración rechaza cuentas existentes que no cumplan la regla. No debe aplicarse a bases existentes sin un plan revisado. Es una limitación deliberada que excluye direcciones internacionalizadas.

Ejecute `npm run bootstrap:owner` solo tras aplicar migraciones y configurar la base. El comando exige terminal interactiva, solicita email y contraseña sin mostrarla, no acepta una contraseña en argumentos y se niega si existe cualquier administrador. Usa el mismo pool protegido que la API, rechaza contraseñas demasiado largas sin truncarlas y no imprime errores internos ni datos ingresados. Las credenciales se eligen e introducen en una terminal privada, nunca como valores predeterminados del código. Durante la consolidación local se ejecutó este bootstrap con autorización explícita sobre `mali_local_development`, tras comprobar que no había administradores; no se reemplazaron cuentas. Véase [administración local](admin-local.md). Respalde y pruebe la recuperación de acceso antes de usarlo en un entorno real.

Tras iniciar sesión, el owner puede indicar explícitamente el nombre visible desde la administración. Solo el owner puede leer o editar estos ajustes; las escrituras requieren origen y CSRF. No se crea un nombre por defecto y este ajuste no configura moneda, pagos ni proveedores de envío.

`POST /api/v1/auth/login` devuelve datos públicos del usuario y CSRF, y establece una cookie de sesión HttpOnly, SameSite Strict y Secure en producción. `GET /api/v1/auth/me` devuelve el usuario; `POST /api/v1/auth/csrf` renueva el CSRF tras una recarga con origen permitido; `POST /api/v1/auth/logout` exige origen y CSRF y revoca la sesión. Las mutaciones de `/api/v1/admin/catalog/products` exigen `X-CSRF-Token`, origen permitido y rol owner o catalog; operations no tiene acceso al catálogo administrativo. La sesión vence tras ocho horas y un nuevo login revoca la sesión anterior presentada en la cookie.

Los hashes de contraseña usan scrypt con sal aleatoria; los tokens opacos se generan con 32 bytes aleatorios y solo sus hashes deben persistirse. Referencias: [OWASP: almacenamiento de contraseñas](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP: sesiones](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Node crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

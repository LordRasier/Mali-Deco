# Compatibilidad MariaDB: estado y prueba local

La API usa el driver `mariadb` de TypeORM con `mysql2` y `synchronize: false`. La prueba de migración, operaciones y reversión pasó sobre MariaDB 10.4.32 de XAMPP en una base local creada exclusivamente para pruebas y dejada vacía. También se aplicaron las migraciones en la base nueva `mali_local_development` y se verificaron por HTTP local ajustes, listado, ficha y resolución del carrito con datos sintéticos que luego se retiraron. No se crearon cuentas ni se modificó la configuración global. El corte aún no es apto para datos reales: faltan revisión independiente y validación de la aplicación completa.

El servidor observado no habilitaba modo estricto por defecto. Cada conexión entregada por el pool de la aplicación activa `STRICT_TRANS_TABLES` en su sesión y comprueba que el modo estricto y las restricciones CHECK estén activos; si falla la configuración o verificación, descarta la conexión y no entrega una conexión insegura. La prueba real incluyó dos conexiones simultáneas, reutilización y rechazo de una conexión con CHECK desactivados. No se cambia el modo global. TypeORM no ofrece un inicializador de sesión para este driver; se protege el método de adquisición del pool de la versión fijada y se rechazan formas incompatibles o replicación. Cualquier actualización de TypeORM o mysql2 exige repetir las pruebas de pool.

Solo en desarrollo, una contraseña vacía requiere `NODE_ENV=development`, `DB_HOST=127.0.0.1`, `DB_PASSWORD` explícitamente vacío y `DB_ALLOW_EMPTY_PASSWORD=1`; en producción o para otros hosts se rechaza. La API escucha solo en `127.0.0.1`. Una cuenta `root` local sin contraseña conserva privilegios amplios de base de datos: esta opción es únicamente para la computadora de desarrollo y no es configuración de producción. El arranque no crea cuentas. Solo `npm run dev` carga el archivo opcional `.env`, sin reemplazar variables exportadas; las pruebas, `npm start` y producción no lo consumen.

Las migraciones históricas se ajustaron para un esquema nuevo: `utf8mb4_unicode_ci` reemplaza `utf8mb4_0900_ai_ci`, las validaciones usan `REGEXP BINARY` y la reversión de CHECK usa `DROP CONSTRAINT`. La comparación de emails usa bytes exactos; los emails siguen limitados a ASCII imprimible en minúsculas y sin espacios. El cotejo general sigue siendo insensible a mayúsculas y acentos, pero `utf8mb4_unicode_ci` no es idéntico a la colación Unicode 9 de MySQL: pueden variar comparaciones y orden para algunos caracteres. Debe verificarse contra los datos concretos. En MariaDB las colaciones binarias pueden ignorar espacios finales al comparar; los emails canónicos los prohíben y el lookup compara bytes. Las diferencias y restricciones de SKUs y slugs deben probarse sobre el servidor antes de uso real.

No hay migración automática ni conversión de datos desde una base MySQL existente. Las migraciones ya ejecutadas no se vuelven a aplicar por cambiar sus archivos. No ejecutar este corte sobre una base existente; una futura transición necesita inventario, respaldo, detección de colisiones, plan de transformación, reversión y revisión independientes. El DDL de MariaDB confirma implícitamente: una falla puede dejar un esquema parcial; no reintentar ni borrar datos sin inspección y autorización.

## Preparación de una prueba aislada

1. La persona responsable debe iniciar el servidor local por su flujo habitual y disponer de una cuenta autorizada y una base nueva, exclusiva y vacía llamada `store_integration_test`. La prueba no crea cuentas ni bases; no usar una base preexistente con datos ni reutilizar la de otra aplicación.
2. Usar una terminal privada en la computadora local. Configurar `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_DATABASE=store_integration_test`, `DB_USERNAME`, `DB_PASSWORD` y `MARIADB_INTEGRATION=1` solo para ese proceso. Introducir el secreto mediante el mecanismo privado de la terminal o del sistema; no escribirlo en el repositorio, mensajes, historial ni logs. Solo para una prueba local expresamente autorizada con `root` sin contraseña se puede añadir `MARIADB_INTEGRATION_EMPTY_PASSWORD=1` y usar un marcador no secreto en `DB_PASSWORD`: el harness sustituye el marcador por contraseña vacía exclusivamente en esa conexión de prueba.
3. Ejecutar `npm run test:integration`. La prueba establece modo estricto en una sola conexión temporal y verifica servidor MariaDB, CHECK habilitados y base vacía antes de aplicar migraciones; después prueba operaciones y restricciones y revierte las tablas que ella creó. No cambia ajustes globales ni la configuración de las conexiones de la API. Si falla, conserva el esquema para diagnóstico: no borrar ni repetir hasta inspeccionarlo.
4. Al terminar, retirar las variables sensibles de la terminal. Cerrar la sesión y gestionar la cuenta o base temporal según las instrucciones del responsable; no se automatiza su eliminación.

La prueba específica del pool se ejecuta por separado desde `apps/api`: configurar la conexión local de desarrollo con `DB_DATABASE=mali_local_development` y `MARIADB_POOL_INTEGRATION=1`, y ejecutar `node --import tsx --test tests/integration/strict-pool.integration.ts`. Solo hace consultas y cambia variables de sus propias sesiones. Mantener `MARIADB_INTEGRATION` sin activar al ejecutar esta prueba: la prueba de migraciones usa otra base exclusiva.

Fuentes: [driver TypeORM](https://typeorm.io/docs/drivers/mysql/), [REGEXP de MariaDB](https://mariadb.com/docs/server/reference/sql-functions/string-functions/regular-expressions-functions/regexp) y [ALTER TABLE de MariaDB](https://mariadb.com/docs/server/reference/sql-statements/data-definition/alter/alter-table).
